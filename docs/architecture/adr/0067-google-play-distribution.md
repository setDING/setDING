# ADR-0067: Google Play next to Obtainium for Android

- **Status:** Accepted
- **Date:** 2026-11-27

## Context

ADR-0021 distributes the Android app only through the GitHub Releases, installed
and updated with Obtainium. Google Play was rejected there because it needed a
developer account and a review, which was overkill for band members during early
development.

The owner has now created a Google Play developer account. Obtainium is a hurdle
for most musicians: they must install an app from outside any store, allow
installs from unknown sources and add the repository as a source. Play installs
and updates the app the way people expect, and lets organizations that roll out
tablets use managed Google Play.

Forces:

- Android installs an update only when it is signed with the **same key** as the
  installed app. Play App Signing signs the APKs Play delivers with an *app signing
  key* that Google keeps; if that key differs from the release key of ADR-0021, a
  Play install and an Obtainium install of `app.setding` are two incompatible
  apps: switching needs an uninstall, which loses the local library.
- The App Links of ADR-0065 are verified against the SHA-256 fingerprints in
  `SETDING_ANDROID_CERT_SHA256` (`assetlinks.json`); every signing key needs its
  fingerprint there.
- Play accepts only Android App Bundles (AAB) for new apps, and every `versionCode`
  must be higher than the previous one.
- Play policy forbids an app from Play to update itself by other means. The
  Android app does not self-update; the update check (ADR-0036) only shows a hint
  that points to Obtainium and the GitHub release page.
- Self-hosting (ADR-0063) and people who avoid Google services still need the APK
  from the GitHub Releases.

## Decision

- **Two channels, one app:** Google Play becomes the recommended way to install the
  Android app; the signed APK in the GitHub Releases stays for Obtainium, devices
  without Google Play and self-hosters. Both deliver the same application ID
  `app.setding`, version and build number.
- **One signature:** Play App Signing is set up with the **existing release key**
  of ADR-0021 (exported encrypted with Google's PEPK tool and uploaded in the Play
  Console), not with a key generated by Google. Play installs and Obtainium installs
  can update each other, and `SETDING_ANDROID_CERT_SHA256` keeps one fingerprint.
- **Upload key:** a separate upload key (PKCS12, alias `upload`) signs the AAB that
  CI uploads. It is stored as repository secrets next to the release key
  (`PLAY_UPLOAD_KEYSTORE_BASE64`, `PLAY_UPLOAD_KEYSTORE_PASSWORD`,
  `PLAY_UPLOAD_KEY_ALIAS`, `PLAY_UPLOAD_KEY_PASSWORD`), created by a make target
  like `make android-keystore`. A lost or leaked upload key can be reset through
  Google support; the release key cannot.
- **Release workflow:** the Android job of `release.yml` also builds an AAB
  (`flutter build appbundle --release`, arm64 like the APK) signed with the upload
  key. On a tag build a `play` job uploads it through the **Google Play Developer
  API** with a service account (JSON key as the repository secret
  `PLAY_SERVICE_ACCOUNT_JSON`, access limited to the setDING app and release
  management) to the **internal testing** track, with the version's
  `CHANGELOG.md` section as release notes (shortened to Play's 500 characters, with
  a link to the GitHub release). Promotion to the closed or production track is
  done by the owner in the Play Console. Manual test builds and the beta and itest
  builds (`app.setding.beta`, `app.setding.itest`) are never uploaded.
- **Build number:** stays the workflow's run number (ADR-0021); it grows with every
  run, so Play accepts every uploaded tag build.
- **Update check (ADR-0036):** the app learns its installer from Android
  (`getInstallSourceInfo`). For a Play install the update hint says to update in
  Google Play and opens the store listing instead of the GitHub release. The app
  cannot tell whether Play already offers the new version (review, manual
  promotion), so the hint stays a hint (no dialog), as today.
- **Store listing:** name, descriptions and screenshots in the six UI languages
  (ADR-0008), taken from the website and `docs/screenshots/`; the privacy policy is
  the website's privacy page; account deletion (a Play requirement) is the existing
  in-app deletion (ADR-0052) plus a web page that explains it.

## Alternatives considered

| Option | Pros | Cons |
|---|---|---|
| Stay with Obtainium only (ADR-0021) | No store review, no Google account, no extra secrets | Hard to install for most musicians; no managed Google Play for organizations |
| Play only, drop the GitHub APK | One channel, Play handles updates | Self-hosters and devices without Google Play lose the app; Obtainium users must reinstall |
| Play App Signing with a key generated by Google | Simplest setup in the Play Console; Google keeps the key safe | Play and Obtainium installs are incompatible (uninstall to switch, local data lost); a second fingerprint in `assetlinks.json` |
| **Play App Signing with the existing release key** (chosen) | Both channels update each other; one fingerprint | The release key must be exported once with PEPK; a leaked release key affects both channels |
| Upload the AAB by hand | No service account | A manual step in every release that can be forgotten; Play falls behind the GitHub Release |
| **Upload by CI to the internal track** (chosen) | Every release reaches Play without a manual upload; production stays a deliberate step | A service account key as a long-lived secret; the first upload must still be done by hand |
| fastlane supply instead of a GitHub Action | Also manages the store listing as files | Ruby toolchain in CI for one upload step |

## Consequences

- A release (ADR-0021) additionally ends with the AAB in the internal track; the
  owner promotes it to production in the Play Console after a check on a device.
  The release is only "done" for Android users of Play after that promotion.
- The **first** AAB must be uploaded by hand in the Play Console (the API cannot
  create the app's first release), together with the opt-in to Play App Signing
  with the release key.
- New personal Play developer accounts must run a **closed test with at least 12
  testers for 14 days** before they may publish to production; organization
  accounts are exempt. The band members are the natural testers.
- Play's review and policies apply: data safety form, content rating, target API
  level (Flutter's `targetSdkVersion` follows the newest Android with each Flutter
  upgrade), the declared permissions (USB/MIDI, camera for QR codes, notifications).
- More long-lived secrets: the upload key and the service account key, backed up
  by the owner outside GitHub like the release key.
- `docs/development/releases.md` describes the Play steps, the website's
  installation page links to the Play listing first and to Obtainium second.
- ADR-0021 stays in force for the GitHub Releases and the APK; it is extended, not
  superseded.
